# AGENTS.md — operating rules for this repository

`README.md` is the **product**: a curated list a reader can scan. It carries entries, measured numbers, and the claims those numbers rest on. Everything about how we produce, clean, and refresh the list lives in `INTAKE.md` and here, not there. If a sentence explains our procedure rather than helps a reader choose a project, it belongs in one of those two files.

`CONTRIBUTING.md` is the short version for human PR authors. `AGENTS.md` and **`INTAKE.md`** together are the full operational spec for anyone (agent or human) maintaining the corpus. Two procedures are large enough to need their own file. Getting a candidate *in* is **`INTAKE.md`**: the A1–A3 admission tests, the filing axis, the method labels, the shape of an entry line, the three-stage pipeline into `entries.json` and the two READMEs, and where candidates come from. The monthly review of entered repositories, with its triggers, output format and the work an agent may do per flagged row, is **`RECHECK.md`**. This file keeps the removal side, the sourcing ledger, the legal record, the refresh automation and the language mirror, plus the pointers and the tests the other two cite.

## Repository layout

We laid this out on the owner's instruction of 2026-10-17 (「重新规划一下目录结构」), by audience and by whether a file is committed:

```
README.md  README.zh-CN.md  CONTRIBUTING.md  AGENTS.md  INTAKE.md  RECHECK.md  LICENSE
data/entries.json  data/decisions.jsonl                   the corpus and the ledger — committed
data/measurement/  data/cache/                            snapshot-, candidates-, quality-, read-, recheck- TSVs;
                                                         API responses; the github/dmca clone — gitignored,
                                                         so a fresh clone starts with these two absent
scripts/{preflight,quality,merge,render,parse,decide}.py   the three stages and the ledger
scripts/{verify,recheck,check-i18n}.py                     refresh, look-back, mirror gate
scripts/census/                                            re-runnable enumeration queries; their 2026-10-16
                                                         rows were deleted, measurement is not kept
```

Two placements are forced, not chosen. `README.md` stays at the repository root because `awesome-lint` only accepts a root README, and that is the structure gate. `AGENTS.md` stays at the root because an agent harness reads the operating spec from there automatically. A subdirectory would stop it loading. The spec's own cross-references (`INTAKE.md` and `RECHECK.md` as bare names) would then resolve against the wrong directory.

Everything the pipeline *writes as evidence* is under `data/`. That is why `.gitignore` is two directory patterns rather than one per artefact file. A fresh clone starts with `data/measurement/` and `data/cache/` absent, and `git add scripts/` can no longer pick up a measurement file by accident.

## Removal: the four reasons an entry leaves

Delete an entry from **both** READMEs in one commit for exactly one of four reasons. The commit message names the reason, and the paragraph that absorbs the entry's facts repeats it. Nothing else removes a line.

| Reason | Read before acting | Where the record goes | What happens to the line |
| --- | --- | --- | --- |
| **Gone** — the repository 404s. | `GET /repos/{owner}/{repo}` returns 404, and `verify.py links` confirms it — so it is not an anonymous-quota artefact. | `## Takedown and legal record` when a notice explains it. Otherwise the `## Sourcing ledger` note beside the claim it carried. | Delete the line. The name survives as plain text, with its last measured ★, its last push date, and the date we found the link dead. |
| **Taken down** — a `github/dmca` notice names it. | The notice file itself, at the path `scripts/recheck.py` prints: the filer, the date, and what the notice actually claims. | `## Takedown and legal record`, where re3/reVC, yuzu and Citra already live. | Delete the line, and **never replace it with a fork or a mirror**. After a takedown the result is not linkable. Citing a derivative as current is the one error this corpus has made a rule against. |
| **Class no longer met** — the project now fails a test it once passed. The rights holder published the source, the artifact has become instrumentation, or its whole class was deleted (the trainers and memory editors, 2026-10-17). | The repository's own credits section and README again, plus its root listing. | A row in `INTAKE.md`'s `## Admission` exclusion table with the test letter. The removed class's history goes in `## Takedown and legal record`. | Delete the line. The four repositories deleted with the `## Trainers and modifiers` section are listed there by name, so a later reader can tell the class was removed rather than never found. |
| **Claim falsified** — the sentence our line quotes is no longer in the repository, or the tree does not hold the reconstruction the line says it holds. | Re-read the README (a quote is re-read at write time, the `storytold/wordcraft` retraction is the worked case) **and** the root file list — which is what turned two ★-50 "rebuilds" into fabrications. | A visible retraction in `## Sourcing ledger`, keeping what was wrong and why it looked right. | Rewrite the line and keep it when the project still clears A1–A3 on what remains. Otherwise drop it from the README as a lead. A note in `## Sourcing ledger` is where it waits, not a queue file. |

- A `stale`, `lic` or `gone` row from `RECHECK.md` says *a line needs reading*, not *an entry is leaving*. Three of the four reasons above can only be decided by a person who has read something. `gone` is the fourth, and the only one the machine establishes on its own. Even then it costs one confirming `GET`.
- Stars, push age, licence, `archived` and how the work was produced are **not** removal reasons, for the same reason they are not admission tests. `archived` in particular means an author marked a finished reconstruction read-only. That is a completion signal we write into the line, not a disqualification.
- After any removal, run `python3 scripts/check-i18n.py`. The mirror gate compares link sets and per-section entry counts, so a one-sided deletion fails it. `awesome-lint` fails on a URL left behind in one file.
- Under `INTAKE.md`'s pipeline, a removal also appends one `decisions.jsonl` line with `decision=remove` and one of the four reasons above: `python3 scripts/decide.py remove --slug … --blocked-on gone --quote "GET /repos/… -> 404" --read-at scripts/verify.py --note …`. `decide.py` will not write the line unless the reason is one of the four. The four reasons are therefore the only way an entry disappears, and every disappearance is auditable without the uncommitted TSVs.

## Refresh automation

`scripts/verify.py` is the only place we obtain numbers. Reviewing the repositories already entered is a separate procedure with its own triggers and output format: **`RECHECK.md`**.

```console
$ python3 scripts/verify.py links            # HEAD/GET every URL in both READMEs, spends no API quota
$ python3 scripts/verify.py refresh          # measure every linked repo, write data/measurement/snapshot-<date>.tsv
$ python3 scripts/verify.py refresh --apply  # additionally write this run's numbers into data/entries.json
$ python3 scripts/render.py                  # regenerate both READMEs from the corpus
$ python3 scripts/render.py --check          # render gate: the two READMEs are exactly that render
$ python3 scripts/check-i18n.py              # English/Chinese mirror gate
$ npx --yes awesome-lint README.md           # structure gate (needs a commit, an origin, and the two topics below)
```

- `awesome-lint` fails with two `remark-lint:awesome-github` errors unless the repository carries the GitHub topics `awesome` and `awesome-list`. The gate reads them from `origin`, so a local clone without a remote reports "must reside in a valid git repository" instead. That is an environment artefact, not a README defect. We set these topics once on the published repository on 2026-10-17: `awesome`, `awesome-list`, `reverse-engineering`, `decompilation`, `reimplementation` (`gh repo edit {owner}/{repo} --add-topic awesome --add-topic awesome-list`, read back with `gh api repos/{owner}/{repo}/topics --jq .names`).
- `--apply` writes this run's numbers into each entry's `measured` (`stars` `forks` `pushed` `archived` `license_spdx` `snapshot`) and advances the corpus `refreshed` date. It prints every value it moved and names every slug the API did not return. **It edits no README**: `render.py` writes both from the corpus, and `render.py --check` is the gate that says so. `created <date>` is a historical fact. `⚠` prose and every description live in `entries.json` as prose or as a literal token. A refresh cannot move them.
- It never *adds* a missing token. An entry whose `tokens` hold no `★` renders no `★`, and no number refresh puts one there. Adding a token is a human editorial act in the corpus.
- The number path is API → `snapshot-<date>.tsv` → `measured` → rendered line. For a candidate too new to be in a snapshot, it is stage 1's `candidates-<date>.tsv` → `measured` → rendered line (`INTAKE.md`). A rendered README never invents a figure that neither file carries.
- Numbers must always equal the newest snapshot. If a refresh was partial, finish the run to fix the numbers. Do not edit `refreshed` in the corpus.
- `data/measurement/` is gitignored whole, and so is `data/cache/` (the API response cache and the `github/dmca` notices clone). They are local or CI evidence, and one file per day is not something to commit. The two files that *are* data and stay tracked are `data/entries.json` and `data/decisions.jsonl`.
- With `GITHUB_TOKEN` or `GH_TOKEN` in the environment, the script authenticates and stops throttling. Unauthenticated, it sleeps 7 s per call. A full pass over every linked slug will **not** fit in the 60 req/h anonymous budget. Expect `MISSING` lines for the tail: that is a quota artefact, not a dead project. Locally, `GITHUB_TOKEN=$(gh auth token) python3 scripts/verify.py refresh --apply` is the way to get a complete pass.
- `.github/workflows/refresh.yml` runs on cron `17 6 * * *` plus `workflow_dispatch`. It runs `refresh --apply` with the workflow's own `GITHUB_TOKEN`, then `render.py`. It gates on `render.py --check`, `check-i18n.py` and `awesome-lint`. It reports `verify.py links` without gating. It opens a PR on branch `data/refresh` **only when the patch actually changed something** — that diff is the corpus plus its render. `.github/workflows/lint.yml` gates the render check, the structure and the mirror on every push and PR. That is what makes "the READMEs are output, never hand-edited" a fact a CI failure can establish rather than a sentence. We deliberately do not auto-commit to `main`. Review a refresh before it lands.

## Language mirror

`README.md` is English. `README.zh-CN.md` is a full mirror: same sections, same entries, same numbers, same `⚠` marks, in that order. `scripts/check-i18n.py` enforces it. It compares both ways:

- the link set,
- the heading list and heading order — **level 2 and level 3 both**, so a `Games` platform subsection has to exist on both sides with the same entry count,
- the entry count per heading,
- the `⚠` count.

It counts as an entry only a bullet whose link is an `http(s)` URL, so `Contents` sub-items are not mistaken for entries. Change both files in one commit, or state in the PR which one you touched. Translation keeps the original product names where no established Chinese title exists. Do not invent Chinese titles for game names.
